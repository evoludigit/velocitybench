VelocityBench — how fast, and why

A reproducible speed test of the tools that turn a database schema into an API. It measures one idea in particular — FraiseQL, which answers a query by reading a pre-computed JSON row from PostgreSQL instead of assembling the answer field-by-field at request time — and shows the result: much faster nested reads, and writes that stay fast because it patches only the rows that changed, in a single measured run.

Start here

What this is. A single, reproducible speed test of the tools that turn a database schema into an API — plus a few hand-written servers as a reference ceiling. It exists to measure one idea: FraiseQL, a GraphQL server that answers a query by reading one pre-computed JSON row from PostgreSQL instead of assembling the answer field-by-field at request time. Pre-computing the row makes nested reads about 5× faster. Writes pay for that: on every write FraiseQL runs an integrated cascade that recomputes the affected precomputed rows to keep reads always consistent — the slowest write measured here. Measured below, including where FraiseQL loses.

Which should you use?

  • Mostly reads, especially nested? FraiseQL — the pre-computed row is already the shape you asked for, and its lead grows with nesting depth.
  • Mostly writes? Probably not FraiseQL — its integrated cascade write is the slowest here, the price of always-consistent precomputed reads. The matcher below weighs your exact mix, and a write-heavy one names a resolver engine, not FraiseQL.
  • A mix, or not sure? Use the matcher just below — it scores every shape from this run, and the winner is not always FraiseQL.

“Isn’t this just a materialized view?”

Fair question — that is the first thing most backend developers think. The difference: on an update FraiseQL keeps the pre-computed rows correct with an integrated, column-aware cascade that recomputes only the affected rows (what this run measures as M1), and serves them through a typed GraphQL API you never hand-write. A plain materialized view is stale until you REFRESH the whole thing; FraiseQL updates incrementally on every write — and that always-on consistency is exactly what costs write speed. See the write trade.

Built by the author of FraiseQL — who has every reason to make it look good, so the method is the guardrail. It is one run on rented hardware anyone can re-rent for a few euros, the raw measurements ship with this page, and the tool is shown losing wherever it loses. A benchmark can only tell you about speed on these shapes — not whether a tool is pleasant to use, well-documented, or right for your team.

Anatomy of a request — what happens per query

Why the nesting cliff happens. The same nested read, three architectures, one lane each — watch where the round-trips come from as depth grows: the resolver lane gains a batched SQL trip per nesting level, while compile-to-SQL and precompute stay at one at any depth.

The classical GraphQL engines here are best-practice, not strawmen: every one batches its nested lookups with a DataLoader (WHERE key = ANY($1)), so there is no N+1 swarm. What the nesting cliff measures is the residual cost — the serial per-level round-trips plus in-process resolver execution — which is exactly what compile-to-SQL and precompute avoid.

These lanes are coloured by request mechanism, not by product family: FraiseQL·v is drawn in the compile-to-SQL lane because that is what it is, and only the pre-computed tv_* path stands apart.

Dots are paced by each engine’s measured p50 for the selected read: playback = p50 × 0.1 s/ms (≈100× slow-motion). At Q2b: async-graphql 6.18 ms→0.62 s · PostGraphile v5 14.0 ms→1.4 s · FraiseQL · tv 4.36 ms→0.44 s. The pace is the only thing the motion encodes — nothing is decorative.

No first-party APQ handshake · excluded by design

  • Hasura CE v2 excluded · 4APQ on Hasura — Hasura CE v2 has no automatic-persisted-query handshake (its allow-lists and query caching are different mechanisms / Enterprise features). Hand-rolling APQ would benchmark custom code.
  • PostGraphile v5 excluded · 5APQ on PostGraphile — v5 first-party persisted operations are a build-time allowlist, not the register-on-first-use sha256 handshake the APQ scenarios measure.
  • Actix (REST) excluded · 6APQ on actix-web-rest — APQ is a GraphQL wire-protocol optimization (persisting a query document by hash); REST requests carry no document, so the scenario is not applicable.
  • Strawberry excluded · 7APQ on Strawberry — Strawberry GraphQL ships no first-party APQ extension (verified against the installed strawberry/extensions inventory); third-party or hand-rolled implementations would not benchmark the framework.

Caching under fire

Caching under fire: the same single-row lookup run two ways — against 20 rotating keys (C3, a cache can never hit) and against a 5-key hot pool (HC3, a cache should hit almost every time). The cache-off variants (v, tv) sit beside the cache-on ones (v+cache, tv+cache) on purpose: if the cache earned its keep, the cache-on rows would jump from C3 to HC3 while the cache-off rows stayed flat. In this run every row is flat — a single-row read is already so cheap (~4 ms) that caching the result saves almost nothing, hot pool or not, and tv+cache is a touch slower with the cache in the path. The chart shows that as-is.

Miss regime

C3 — 20 rotating UUIDs. Each request asks for a different row, so a result cache is cold on every request: the worst case a cache can face.

Hit regime

HC3 — a 5-UUID hot pool. The same handful of rows repeat, so a result cache should serve almost every request from memory: the case caching is built for.

When does precompute pay off?

The one system-level view — every story above is one request at a time, but a real service runs a mix of reads and writes. This models total sustainable load as that read:write ratio changes, and finds the break-even. FraiseQL moves read cost to write time (the cascade builds the precomputed rows), so it needs enough reads per write to amortize that write. At r→0 the curve is the measured write throughput; at r→∞ the measured read throughput. Higher is better; where FraiseQL's line crosses above a rival is the break-even for that pair.

Structural query count — secondary, and counts are not cost. SQL round-trips per workload-unit from the S0 hop model: a per-level resolver does 2–3 trips for a nested read, a compiler or precompute does one. This is why depth hurts resolvers — but a round-trip is not a fixed price, so this layer never decides the winner, and it never leads.

Reading these numbers

The same-run rule
This page renders exactly one benchmark sweep. No cross-run or cross-hardware mixing — the generator refuses two JSON files. The numbers here are the per-cell median of three warm sweeps on one rented box; the first post-seed sweep is discarded as a warm-up, and each cell's run-to-run spread is in the run JSON.
The load generator is not the bottleneck
The load generator (k6) runs on its own dedicated box and drives the system-under-test over a private network — never co-located, never sharing the SUT's cores. A pre-sweep headroom gate points k6 at a null target on the SUT and requires it to sustain far more than any framework serves (the enforced floor is 30,000 RPS, several times the fastest cell in this grid), so these numbers are server-bound, not load-generator-bound. The exact measured headroom and full topology are in the reproduction doc.
Logged tables, not unlogged
The tv_* precomputed tables run LOGGED here — crash-durable, and the conservative choice for a published number. pg_tviews can run them UNLOGGED for more write throughput, but an unclean shutdown then truncates them; this run does not take that trade, so nothing here is inflated by dropping durability. The disk cost of precompute is shown honestly in S6.
Q1 and the TOAST read-cost
FraiseQL leads Q1 — its precomputed tv variants top the field here, not mid-pack. Each tv_user read still detoasts a full precomputed JSONB document, so the read-side cost is real; but in this run it is too small to surface — the tv variants sit level with their JOIN-view (v) siblings at Q1. The precompute trade is paid on writes (the integrated M1 cascade), not on Q1 reads, and FraiseQL's read edge over its own v variants only widens as nesting deepens (Q2b → Q3).
tview trigger scoping
pg_tviews cascade triggers fire only while a FraiseQL framework is under test (tview_trigger_scope = fraiseql-only). Classical stacks run against a vanilla table with the triggers disabled, then tv_* rows are resynced before the next FraiseQL run.
MC1 is a workflow benchmark
MC1 is a workflow benchmark, not raw server speed: it counts the client round-trips needed to reach a consistent state after a write. FraiseQL = 1 request/cycle (the mutation response carries the cascade); classical GraphQL and REST = 2 requests/cycle (mutation + serial re-fetch).
M1 under tviews — integrated cascade
Under logged tviews, M1 is FraiseQL's real write: the integrated column-aware cascade that recomputes the affected precomputed rows so reads stay consistent — the maintenance price of always-consistent precomputed reads, and the slowest write measured here.
Classical M1 — vanilla update
Classical M1 is a single UPDATE on a vanilla table with no derived state to maintain.
The audit-overhead appendix row
fraiseql-tv-audit measures M1 only — an audit-overhead appendix row isolating the cost of audit logging on the mutation path. It is never a full-grid framework.
“Not measured” ≠ excluded ≠ slow
Cells marked “not measured in this run” are wired in the benchmark but were not executed in the run shown. They are distinct from “excluded by design” and are neither slow nor missing on purpose. This publishable run measured the full grid, so no cell carries this status.
