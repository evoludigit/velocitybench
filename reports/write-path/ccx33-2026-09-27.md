# Write-path attribution — Hetzner CCX33, 2026-09-27

**Classification: cascade-bound.** Not fsync-bound, not serialisation-bound. The
lever is pg_tviews differential maintenance.

## Rig

- SUT: CCX33, **AMD EPYC-Milan** (8 vCPU, 32 GiB), fsn1. CCX33 also lands on
  Genoa hosts; this one did not, so these numbers belong to Milan.
- PostgreSQL 17, fraiseql 2.14.0, pg_tviews 0.1.0-beta.17, logged tviews.
- Medium dataset: 10 005 users / 100 005 posts / 500 005 comments.
- The probe ran on the SUT after two full sweeps (the first a discarded
  warm-up), so it measured a fragmented heap. Nothing else was running.

## Population

Fan-out is a property of the row, so both populations were recorded:

| population | users | posts/user | comments authored/user |
|---|---|---|---|
| probe (`ORDER BY id LIMIT 20`) | 20 | 10 (all) | 50 |
| sweep M1 (fraiseql-tv Q1) | 20, different rows | 10 (all) | 50 |

The seed is uniform (0–11 posts per user, mean 10.00), so a bio write is
**12 rows** for any user: tb_user + tv_user + 10 tv_post. The report's "~61" is
1 tv_user + 10 tv_post + 50 tv_comment, which is a **username** change's
fan-out, not bio's.

## Matrix — medians of 3 runs, 400 mutations/cell

`guard_failures` is empty in all 3 runs. Every cell has `stats_flush=quiesced`,
and every cell verified all 20 target rows written.

| cell | rps | rows/mut | HOT | WAL KiB/mut | sync ms/mut | p50 ms | rps range | WAL range |
|---|---:|---:|---:|---:|---:|---:|---|---|
| cascade on, fsync on, c=1 | 368 | 12.0 | 8% | 30.3 | 0.23 | 2.4 | 363–374 | 28.5–35.6 |
| cascade on, fsync on, c=40 | ~~269~~ see below | 12.0 | 8% | 30.3 | 1.4 | 33.3 | 266–285 | 29.8–38.3 |
| cascade off, fsync on, c=1 | 2 089 | 1.0 | 100% | 0.1 | 0.14 | 0.2 | 2 063–2 146 | 0.1 |
| cascade on, fsync off, c=1 | 409 | 12.0 | 8% | 27.6 | 0.00 | 2.2 | 392–418 | 26.5–28.0 |

Run 1 followed the sweeps' last checkpoint and carried 572–896 FPIs per cell,
against 20–79 in runs 2–3. That run is where the top of the WAL range comes from.

## The c=40 cell is a driver artefact

The SQL driver opens one `docker exec psql` per worker, and the cell's
wall-clock includes starting them. Measured on the SUT:

- one `docker exec psql`: 0.07 s
- 40 concurrent: **0.86 s**, which is more than half of the 400-mutation c=40
  cell's 1.49 s wall

Re-measured with 4 000 mutations, so start-up is spread across 10× more work:

| cell (4 000 mutations) | rps | mean ms | p50 ms |
|---|---:|---:|---:|
| c=1 | 407 | 2.4 | 2.3 |
| c=40 (3 runs) | **790** (785–798) | 40.6 | 27.8 |

Concurrency scales **~1.9×** even with the 0.86 s start-up still in the
window. Latency alone implies 40 / 40.6 ms ≈ 985 rps. That matches what the
sweeps saw through GraphQL on the same box (fraiseql M1 ≈ 1 060 rps at
c=40). The matrix's "CONTENTION-BOUND, 0.73×" verdict is wrong. The archbox
0.49× came from the same driver. Re-timed from a database-side barrier, archbox
is ~1.0–1.2× (flat), not negative; see `docs/write-path-attribution.md`,
trap 4. The CCX33 790 figure predates that fix and still includes start-up, so
it is a lower bound.

## Runtime share — medians of 3 runs, c=1, fraiseql-tv

| driver | rps | mean ms |
|---|---:|---:|
| SQL (`benchmark.fn_update_user`) | 381 | 2.42 |
| GraphQL (`updateUser`, port 8816) | 256 | 3.87 |

**+1.45 ms per mutation** is FraiseQL plus HTTP above the database, measured
from a Python client with no connection reuse (archbox: +1.4 ms). GraphQL
cells report `stats_flush=flushed-by-timeout`: the counters caught up without
terminating any backends.

## Reading

- **Cascade: 5.68×.** Disabling pg_tviews takes a mutation from 12 rows to 1,
  from 30.3 KiB of WAL to 0.1 KiB, and HOT from 8% to 100%. Per mutation it is
  ~2.2 ms of the 2.5 ms (cascade-off mean 0.3 ms). It also sets how long each row lock is held, so it
  bounds the c=40 ceiling as well. That last point is inferred, not measured
  separately.
- **Durability: 1.11×.** `wal_sync_time` is 0.23 ms of a 2.5 ms mutation. On
  this device, storage, ZFS or SLOG work would not move M1.
- **Concurrency: positive (~1.9–2.4×),** so the "neither, with c=40 ≤ c=1"
  branch does not apply. M1's 20-row profile costs throughput (40 workers,
  p50 28 ms) but is not the ceiling.
- **Runtime: +1.45 ms,** real but secondary. It is about 60% on top of a
  2.4 ms database write that is itself ~88% cascade.

Archbox → CCX33: the cascade share grew (2.66× → 5.68×), mostly because
cascade-off got faster (1 446 → 2 089 rps). The fsync share stayed small
(1.20× → 1.11×). The runtime share is unchanged (+1.4 → +1.45 ms).
